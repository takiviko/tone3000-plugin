# Android build of the TONE3000 plugin

## Context

The user wants an Android build of the TONE3000 JUCE plugin, suspecting (correctly) that the **Standalone** format is the only viable target — JUCE plugin formats (VST3/AU/AAX/LV2/CLAP) all assume a desktop plugin host, which Android has none of.

This repo already has a working precedent for exactly this shape of problem: an **iOS Standalone port** (`T3K_IOS`, documented in `docs/ios.md`), built on JUCE's officially-supported CMake+Xcode-generator path. Android is a materially harder version of the same problem: **JUCE has no official CMake support for Android at all.** Officially, Android apps are Projucer-generated Android Studio/Gradle projects, where Gradle invokes CMake only as a sub-build (`externalNativeBuild`) for the native `.so`. This repo has zero Projucer/.jucer files by design — it patches JUCE's own source at configure time instead (10+ idempotent patches already in `CMakeLists.txt`, e.g. ALSA use-after-free fixes, WebKitGTK cookie persistence, the AudioDeviceManager sample-rate regression). The user chose to extend that same idiom rather than introduce Projucer, accepting the added risk of building on an unofficial/experimental JUCE code path (confirmed via a community reference project, `atsushieno/android-juce-cmake`, whose author warns of Android-specific audio-channel issues and describes the whole approach as unsupported).

Decisions already made by the user (do not re-litigate):
1. **Approach**: hand-roll the Android Studio/Gradle wrapper (new `android/` directory), point its `externalNativeBuild` at this repo's existing CMakeLists.txt via the NDK CMake toolchain — no Projucer, not even one-time.
2. **Audio backend**: Oboe (Google's low-latency library), not OpenSL ES.
3. **Form factor for v1**: tablet, landscape-only — mirrors the iOS port exactly (same desktop-aspect UI, letterboxed/centered), reusing the existing `IS_COARSE_POINTER` touch-ergonomics gating in the React UI, which already anticipates "iPad or Android or Windows tablet."

Because this is a novel, unproven path in a way the iOS port was not (iOS rode a fully-supported CMake/Xcode flow; Android does not), the plan is **spike-first and incremental**, not a single PR: the biggest unknown (does JUCE 9.0.1's dlsym-based Android app bootstrap actually work, and can the missing symbol visibility be patched) gets retired in isolation before touching this repo's real complexity (NAM, Oboe, the React UI, the 10 existing JUCE patches).

## Phase 0 status: DONE (2026-09-15)

A trivial JUCE 9.0.1 GUI app was cross-compiled via CMake + the Android NDK, wrapped in a hand-rolled Gradle project, installed on a Pixel Tablet emulator (API 34), launched, and rendered on screen — confirmed via screenshot. This retired the core risk and surfaced concrete facts that **change several of Phase 1's assumptions below** (the phase 1/2/3 sections after this one are the *original* plan and are kept for the record, but should be read alongside these corrections):

- **No JUCE source patch was needed** for `juce_CreateApplication` visibility in this spike. `juce_add_gui_app()` does not set `CXX_VISIBILITY_PRESET hidden` on Android (verified by reading `JUCEUtils.cmake`), so the symbol exported with default visibility and `dlsym` found it immediately (verified with `llvm-nm`). The **real Standalone plugin target** (`juce_add_plugin(... FORMATS Standalone ...)`) *does* go through `_juce_link_plugin_wrapper`, which explicitly sets `CXX_VISIBILITY_PRESET hidden`/`C_VISIBILITY_PRESET hidden` on **every** platform including Android (`JUCEUtils.cmake:1509-1511`) — so a fix is still likely needed there, but it may be as simple as `set_target_properties(<target>_Standalone PROPERTIES CXX_VISIBILITY_PRESET default C_VISIBILITY_PRESET default)` after the `juce_add_plugin()` call, **not** a `file(READ)`/`string(REPLACE)` source patch. Verify this directly against the real Standalone target in Phase 1 before assuming either way.
- **Oboe needs no new CPM dependency.** JUCE 9.0.1 vendors Oboe directly inside `modules/juce_audio_devices/native/oboe/` and builds it automatically as part of the `juce_audio_devices` module (confirmed: it compiled without any explicit link, since JUCE's CMake module registration walks and configures every module under `modules/` regardless of what's actually linked). Drop the "new CPM dependency for Oboe" line from Phase 1 entirely.
- **NDK version is a hard constraint, not a free choice.** The latest NDK (30.0.16248370) is incompatible with JUCE 9.0.1's vendored Oboe copy: NDK 30's own `<aaudio/AAudio.h>` now declares `AAudio_FallbackMode`/`AAudio_StretchMode`/`AAudioPlaybackParameters`/`AAudio_DeviceType`, which collide (duplicate/conflicting redefinitions) with Oboe's own compatibility shims for those same symbols in `AAudioLoader.h`. **NDK 27.2.12479018 (r27c) is confirmed working.** Pin to this (or another pre-AAudio.h-expansion NDK) in `android/app/build.gradle.kts`'s `ndkVersion`, not whatever is newest.
- **`ANDROID_PLATFORM` must be >= 29.** Below API 29, `juce_graphics`'s Android system-font-matching code (`juce_Fonts_android.cpp`) fails to *compile* (hard "is unavailable: introduced in Android 29" errors from Clang, despite the calls already being wrapped in `__builtin_available(android 29, *)` guards in JUCE's own source — root cause not fully diagnosed, but raising the floor is a confirmed, simple fix). This effectively sets **`minSdk = 29` (Android 10)** as the practical floor for this project, which should be raised to the user as a decision to confirm/re-confirm for the real plugin (v1 is tablet-only anyway, so a 2019+ floor is very likely fine, but it's a departure from whatever `minSdk` might otherwise have been assumed).
- **The CMake target itself must be named `juce_jni`.** JUCE's `_juce_set_output_name()` deliberately skips renaming the build output on Android (`if (NOT CMAKE_SYSTEM_NAME STREQUAL "Android")` in `JUCEUtils.cmake:628`), so the CMake target name *is* the `.so` basename. JUCE's Java glue (`Java.java`) hardcodes `System.loadLibrary("juce_jni")`, so whatever `juce_add_plugin()`/`juce_add_gui_app()` target name is used for the Standalone build on Android must literally be `juce_jni` (confirmed working: `set(APP_TARGET juce_jni)` before the `juce_add_gui_app()` call, conditional on `CMAKE_SYSTEM_NAME STREQUAL "Android"`).
- **Two more required, JUCE-CMake-API-undocumented compile definitions**, without which the stock `JuceActivity.java` throws `UnsatisfiedLinkError` on the very first `onResume()` (confirmed: this exact crash was hit and fixed during the spike):
  - `JUCE_PUSH_NOTIFICATIONS_ACTIVITY="com/rmsl/juce/JuceActivity"` (or a custom Activity subclass's JNI path) — without it, `juce_Windowing_android.cpp` never compiles in the C++ implementations of `JuceActivity.java`'s `native` `appOnResume()`/`appNewIntent()` methods, which that Java file declares unconditionally.
  - `JUCE_PUSH_NOTIFICATIONS=1` — required alongside the above; without it, the `appNewIntent` path references `juce_handleNotificationIntent()` with no visible declaration (hard compile error). With it, JUCE's own `juce_PushNotifications_android.cpp` (part of `juce_gui_extra`) provides a real implementation automatically — no push-notification/Firebase setup is actually pulled in beyond this, and no stub needs to be hand-written.
  - Confirmed nothing in `extras/Build/CMake/*.cmake` sets either of these automatically — JUCE's CMake API has no "just works" Android activity story here.
- **`JuceActivity`/`JuceApp` (JUCE's stock Java classes) worked with zero custom Java code** for this trivial spike — no custom `MainActivity.java` was needed at all, just referencing `com.rmsl.juce.JuceActivity`/`com.rmsl.juce.JuceApp` directly in `AndroidManifest.xml`. Confirmed exact Java source-set paths needed for JUCE 9.0.1 (differs slightly from the original plan's placeholder paths): `juce_core/native/java/app`, `juce_core/native/javacore/app`, `juce_core/native/javacore/init`, `juce_gui_basics/native/java/app`, `juce_gui_basics/native/javaopt/app`.
- **Host MSVC (cl.exe) is required on the build machine even when only targeting Android** — JUCE's CMake build always compiles a small host-native helper tool (`juceaide`, used for binary data/icon/plist generation) as part of every configure, regardless of target platform. This was already resolved (Visual Studio Build Tools 2022 already present on this machine at `Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`, just not the default `Program Files` location), but is worth calling out explicitly as an environment prerequisite for Phase 1/CI.
- **Known-good toolchain versions for this JUCE 9.0.1 checkout**: AGP 9.4.0, Gradle 9.7.1 (needed — Gradle 8.9 fails outright against JDK 25, which is what Android Studio's bundled JBR ships), compileSdk/targetSdk 36 (34 fails to compile `ComponentPeerView.java`'s `APPEARANCE_LIGHT_CAPTION_BARS`, added in API 35), minSdk 29, NDK 27.2.12479018, CMake 4.1.2 (SDK-bundled), `project(... VERSION x.y.z ...)` required in the top-level `CMakeLists.txt` or JUCE's CMake errors ("Target juce_jni must have its VERSION argument set").

**Not yet re-verified against these findings**: whether the real `juce_add_plugin(FORMATS Standalone)` path (as opposed to this spike's `juce_add_gui_app`) needs the visibility override mentioned above, and whether NAM/Oboe/curl/JACK gating (Phase 1 below) needs adjustment now that Oboe is known to be vendor-bundled rather than a new dependency. Both are next up when Phase 1 resumes against the real repo.

## Phase 1 & 2 status: DONE (2026-09-15)

`T3K_ANDROID` CMake plumbing landed in the real repo (`CMakeLists.txt`, `plugin/CMakeLists.txt`), plus a real hand-rolled `android/` Gradle project. **The actual TONE3000 plugin (not a spike) now builds, installs, and launches on an Android emulator**: `TONE3000Processor` constructs, enumerates real Android audio I/O devices, and Oboe opens a real AAudio output stream — confirmed live in logcat, not just "no crash." New findings on top of Phase 0's:

- **The Phase 0 visibility prediction was correct and is now confirmed on the real Standalone target.** `juce_add_plugin(... FORMATS Standalone ...)` (unlike the spike's `juce_add_gui_app`) *does* go through `_juce_link_plugin_wrapper`, which sets `CXX_VISIBILITY_PRESET hidden`. Verified directly with `llvm-nm`: without a fix, `juce_CreateApplication` showed as `t` (local) and was entirely absent from the dynamic symbol table (`nm -D`); with `set_target_properties(${PROJECT_NAME}_Standalone PROPERTIES CXX_VISIBILITY_PRESET default C_VISIBILITY_PRESET default)` added right after `juce_add_plugin()`, it shows as `T` (global/exported). **No JUCE source patch was needed** — this one-time property override was sufficient, confirming Phase 0's guess over the original plan's assumption of a required source patch.
- **Critical correction to Phase 0's push-notification-define finding**: `juce_add_plugin()` splits into a **shared-code static library** target (`${PROJECT_NAME}`, e.g. `TONE3000` — every JUCE module, including `juce_gui_basics.cpp`/`juce_Windowing_android.cpp`, compiles here) and thin per-format **wrapper** targets (`${PROJECT_NAME}_Standalone`, etc. — these only link against the static library, they don't recompile any of it). Phase 0's spike used `juce_add_gui_app()`, which has no such split (one target, one place for the define), which is why applying `JUCE_PUSH_NOTIFICATIONS_ACTIVITY`/`JUCE_PUSH_NOTIFICATIONS=1` to `${PROJECT_NAME}_Standalone` seemed to work there. On the real plugin, that placement **compiled cleanly but still crashed on-device** with the exact same `UnsatisfiedLinkError` on `JuceActivity.onResume()` Phase 0 first hit — because `juce_gui_basics.cpp` (where the fix actually needs to land) is compiled into `${PROJECT_NAME}`, not the wrapper, and a `PRIVATE` define on the wrapper never reaches it. **Fix: set both defines on `${PROJECT_NAME}` instead.** Confirmed working after moving them: app launches, no crash, "Displayed" in logcat. This is the kind of mistake that's easy to make again in Phase 3+ — any future Android-only compile definition needs to be checked against which of the two targets actually compiles the affected file, not assumed to be interchangeable.
- **NAM's `PLATFORM_ID:Android` generator expression works as predicted** — extending the Linux three-item whole-archive form (`-Wl,--whole-archive` / `NAM` / `-Wl,--no-whole-archive`) to also match `Android` (via `$<$<PLATFORM_ID:Linux,Android>:...>`) linked cleanly; the model-architecture registrations survived (no "No config parser registered for ..." at runtime — confirmed implicitly by the processor constructing and enumerating devices without error).
- **The `UNIX AND NOT APPLE` gotcha was real** and hit exactly as predicted: the un-restructured `else()` branch's unconditional `find_package(X11 REQUIRED)` did try to run for Android (`UNIX` is `TRUE` there) and would have hard-failed the configure. Fixed by adding an explicit `elseif (T3K_ANDROID)` branch before the generic `UNIX`/X11 one. **Correction to the original plan's assumption that `WindowKeyEvents.cpp` "should simply not compile on Android"**: it doesn't need to be excluded at all — the file already isolates its per-platform implementations behind `#if`/`#elif` on a single shared `forwardKeyToHost()` declaration (the same pattern `WindowKeyEvents.mm` already uses for a real-macOS-vs-no-op-iOS split), so the cleanest fix was adding one more `#if JUCE_ANDROID` no-op branch *inside that file* (mirroring the existing iOS stub in `WindowKeyEvents.mm`) and compiling it unconditionally on Android too, rather than excluding it from the Android source list and hoping nothing links against `forwardKeyToHost()`. (Something does: `EditorWebViewSetup.cpp`'s JS-callable native function forwards Space/Enter to the host DAW — on Android there is no host DAW, same reasoning as the existing iOS no-op, so this needed a definition, not an omission.)
- **`AudioPermissions.cpp`'s existing non-Apple stub compiles and runs as-is on Android for now** (always reports `MicStatus::granted`) — this is known-incorrect per the original plan (Android actually enforces `RECORD_AUDIO` at the OS level) and is still open Phase 3 work; for this verification pass the permission was granted manually via `adb shell pm grant ... RECORD_AUDIO` before launch.
- **New, Android-specific WebView finding for Phase 4**: a Debug build correctly points the WebView at the Vite dev server (`http://localhost:5173/`), matching the already-documented iOS Debug-build behavior (`docs/ios.md`: "A Debug iOS build points the WebView at http://localhost:5173/, so it shows a dead page") — **but on Android this additionally hits `net::ERR_CLEARTEXT_NOT_PERMITTED`**, since Android's WebView blocks plain-HTTP traffic by default from API 28+ (this project's `minSdk` is 29). iOS's WKWebView has no equivalent restriction, so this is a genuinely new platform difference, not just a repeat of the iOS caveat. Fixable with a `network_security_config.xml` allowing cleartext for `localhost` (or `android:usesCleartextTraffic="true"`), for local dev-server iteration only — not attempted yet.
- **A second, more fundamental WebView gap confirmed via a real Release build** (built, zipaligned, signed with the debug keystore, installed, and launched on-device — this bypasses the dev-server question above entirely and tests the embedded-binary-data path JUCE uses in Release/production): the WebView actually tries to load **`https://juce.backend/index.html`** and fails with **`net::ERR_NAME_NOT_RESOLVED`** — a real DNS lookup attempt, not an intercepted virtual request. `juce.backend` is JUCE 9's internal virtual-host convention for serving embedded webview binary data (intercepted natively by WKWebView/WebView2 on iOS/desktop), and **Android's WebView backend does not intercept it out of the box** the way the other three platforms' backends do. This directly confirms the plan's Phase 4 risk framing ("do not assume it just works") as a real, concrete gap rather than a hypothetical one: loading the embedded React bundle at all on Android needs either JUCE-side Android support for this virtual-host mechanism that isn't wired up by this repo's current CMake integration, or an Android-specific interception (e.g. `WebViewAssetLoader`/`shouldInterceptRequest()`) added on top. **Unsolved — the single biggest open item for Phase 4**, more fundamental than the cleartext-HTTP issue above since it blocks the production path, not just local dev-server iteration.
- Confirmed working toolchain end to end for a **real, full plugin build** (not just the trivial spike): AGP 9.4.0, Gradle 9.7.1, compileSdk/targetSdk 36, minSdk 29, NDK 27.2.12479018, `-DANDROID_PLATFORM=android-29`, `externalNativeBuild.cmake.targets = ["TONE3000_Standalone"]` to restrict Gradle's CMake sub-build to just the one meaningful target.
- New files: `android/settings.gradle.kts`, `android/build.gradle.kts`, `android/gradle.properties`, `android/local.properties` (gitignored — machine-specific SDK path), `android/app/build.gradle.kts`, `android/app/src/main/AndroidManifest.xml`. No gradle wrapper jar/scripts committed yet (built and run so far via a standalone Gradle 9.7.1 distribution outside the repo) — generating and committing the real `gradlew`/`gradlew.bat`/wrapper jar is still open.
- **Still open / not yet done**: committing a real Gradle wrapper (vs. today's external Gradle install), the WebView content gap above, `docs/android.md` write-up, CI (Phase 6).

## Phase 4 status: substantial progress, one open item (2026-09-15)

Went in expecting to confirm or refute the "Android's WebView backend doesn't intercept `juce.backend`" finding from the Phase 1/2 session. That finding turned out to be **wrong** - and two real, separate bugs were found and fixed in its place, following the trail all the way to a working (rendering, booting) embedded UI, with one open item remaining.

- **Correction: the `juce.backend`/`ERR_NAME_NOT_RESOLVED` finding from the Phase 1/2 notes was a false alarm.** Root cause: `ui/` had never been built for any Android test up to that point, so the embedded `WebAssets` binary data was only ever the single-space placeholder `plugin/CMakeLists.txt` falls back to. `TONE3000Editor::getResource()` (`plugin/src/Editor.cpp`) correctly returned `std::nullopt` for a nonexistent `index.html`, Android's `handleResourceRequest` correctly fell through to real network resolution for the unhandled request, and `juce.backend` predictably failed DNS lookup. After actually running `npm ci && npm run build` in `ui/` and forcing a CMake reconfigure (same "reconfigure after every UI change" requirement `docs/ios.md` already documents, since `file(GLOB_RECURSE)` over `webview/*` runs at configure time) - **the real embedded React UI loaded and executed on Android**, confirming the `juce.backend` resource-provider interception (`handleResourceRequest` in `juce_WebBrowserComponent_android.cpp`) works correctly out of the box. No patch needed for this part.
- **Real bug #1, found once the real UI was running: `window.localStorage`/`sessionStorage` are `null`.** `JuceWebView`'s constructor (`JuceWebViewClasses.java`) configures several `WebSettings` but never calls `setDomStorageEnabled(true)`, unlike every other JUCE WebView backend. `WebBrowserComponent::Options` has no Android-equivalent of `WinWebView2`/`AppleWkWebView`/`LinuxWkWebView`, so there's no supported way to reach this from application code.
- **The DOM storage fix required discovering a second, non-obvious fact about how JUCE ships this Java class**: patching the `.java` source text (`native/java/app/.../JuceWebViewClasses.java`) has **zero runtime effect**. JUCE compiles this class once, ahead of time, gzips the resulting `classes.dex`, and embeds it as a raw byte array (`juceWebViewClasses[]`) directly inside `juce_WebBrowserComponent_android.cpp`, loaded at runtime via `DECLARE_JNI_CLASS_WITH_BYTECODE` - the `.java` file is reference-only (this class is also, confirmed via `dexdump` on a real built APK, entirely absent from the app's own compiled classes; only the Java glue this project explicitly listed in `sourceSets` - `JuceActivity`, `JuceApp`, etc. - actually gets compiled into the APK). Verified the hard way: two full clean rebuilds with only the `.java` patch in place produced byte-identical on-device screenshots of the same crash. The actual fix required regenerating the embedded bytecode: `javac --release 17` (not whatever JDK is on `PATH` - d8 rejects newer class file versions) against the patched source, `d8 --min-api 23` to dex it, `gzip`, then swapping the entire array in `juce_WebBrowserComponent_android.cpp` for the new bytes. The regenerated bytes are checked into `cmake/android-juce-webview-classes.dex.gz.inc` (with the exact regeneration recipe in its own header comment) and substituted in by a new `T3K_ANDROID_DOM_STORAGE_BYTECODE` patch in the root `CMakeLists.txt`, in the same configure-time-patch idiom as everything else. **Verified fixed on-device**: the `Cannot read properties of null (reading 'getItem')` error boundary no longer appears; console log shows `"TONE3000 UI booted"` with no error following it.
- **Real bug #2, now the last known blocker: the booted UI renders as a blank black screen.** No crash, no console error, "TONE3000 UI booted" logs successfully, but the screen stays solid black indefinitely (confirmed stable across two screenshots 5+ seconds apart, not a loading transient). This matches, precisely, the risk already flagged in the Phase 1/2 notes: Android never gets the `window.__T3K_PLATFORM__` injection iOS gets (`plugin/src/EditorWebViewSetup.cpp`, `#if JUCE_IOS`), so `ui/src/hooks/useUiScale.ts`'s `IS_IOS`-gated fixed-window handling never engages for Android either, despite Android's fullscreen Activity having the exact same characteristic the code comment describes iOS as uniquely having ("the only build whose window is a fixed, full-screen box... there is no corner drag, no host resize request"). The likely mechanism: `fitScale()` reads `document.documentElement.clientWidth/clientHeight`, and without the fixed-window handling, whatever it computes on Android's WebView either floors at the hardcoded 0.05 minimum scale (rendering real content at ~5% size, invisible against the black background) or the resize-wait logic never resolves. **Not yet fixed** - this needs the `IS_IOS` → `IS_FIXED_WINDOW` generalization already scoped in the Phase 1/2 notes (add an equivalent Android injection in `EditorWebViewSetup.cpp`, extend every `IS_IOS`/`t3k-ios` consumption site in the UI), which touches shipped iOS behavior and should be scoped as its own change rather than rushed.
- Confirmed as a byproduct: `IS_COARSE_POINTER`/touch ergonomics still needs no work (unrelated to this bug, per its own platform-agnostic `matchMedia` implementation).

If it fails outright, the fallback is a one-time Projucer-generated Android project used purely as a diff reference (not adopted as a build tool) — flag this to the user explicitly before doing it, since it's a deliberate, temporary exception to decision #1.

## Phase 1 — Native build plumbing (`T3K_ANDROID`)

Mirror the existing `T3K_IOS` flag (`CMakeLists.txt:15-17`, `plugin/CMakeLists.txt:8-18`) with a new `T3K_ANDROID` flag (`CMAKE_SYSTEM_NAME STREQUAL "Android"`), set after `project()` unless Phase 0 shows otherwise (iOS needs its pre-`project()` timing only because of `CMAKE_OSX_DEPLOYMENT_TARGET`, which has no Android equivalent).

**Root `CMakeLists.txt`:**
- New `juce_CreateApplication` visibility patch, in the exact existing idiom (`file(READ)` → sentinel-guarded `string(REPLACE)`/regex → `FATAL_ERROR` if the anchor is missing → `file(WRITE)` → `message(STATUS ...)`), anchor pinned from the Phase 0 spike. Follow the `T3K_*` sentinel naming convention (e.g. `T3K_ANDROID_CREATE_APP_VISIBILITY`).
- New CPM dependency for Oboe (`${LIB_DIR}/oboe`), gated `if (T3K_ANDROID)`, placed alongside the existing JUCE/GoogleTest `CPMAddPackage` calls.
- Decide explicitly (don't let Gradle silently pick): let Gradle's default `externalNativeBuild` inject `-DCMAKE_TOOLCHAIN_FILE=<ndk>/build/cmake/android.toolchain.cmake` (the standard, best-supported path) rather than fighting it with CMake's own built-in Android cross-compilation variables.

**`plugin/CMakeLists.txt`:**
- Mirror the deployment-target and format-gating blocks (`plugin/CMakeLists.txt:8-18`, `45-54`): reset `_plugin_formats` to `"Standalone"` only under `T3K_ANDROID`, force `BUILD_AAX`/`BUILD_LV2`/`BUILD_CLAP` off.
- **Divergence from the iOS template to keep in mind**: iOS gets a `_t3k_ios_args` list (`plugin/CMakeLists.txt:194-209`) because JUCE's CMake API has iOS-aware `juce_add_plugin()` arguments (`BUNDLE_ID`, `BACKGROUND_AUDIO_ENABLED`, orientation, etc). **There is no Android-aware equivalent** — package name, permissions, orientation, and icons all live in the hand-authored `android/` Gradle project (Phase 2) instead, not in `juce_add_plugin()`.
- NAM guard (`plugin/CMakeLists.txt:96-98`): extend `if (NOT T3K_IOS)` → `if (NOT T3K_IOS AND NOT T3K_ANDROID)` around `add_subdirectory(NeuralAmpModelerCore)` (its own CMakeLists hard-fails "Unrecognized Platform!" outside Darwin/Linux/Windows).
- NAM force-load linking (`plugin/CMakeLists.txt:437-455`): verify whether CMake reports `PLATFORM_ID` as `Android`, and whether Android's Clang/LLD wants the Linux-style three-separate-items whole-archive form (`-Wl,--whole-archive` / `NAM` / `-Wl,--no-whole-archive`) rather than Apple's single-flag form — confirm empirically, don't assume.
- **Important gotcha**: CMake sets `UNIX` to `TRUE` for Android (Linux-kernel-based), so every existing `if (UNIX AND NOT APPLE)` gate in this file will also silently match Android unless excluded:
  - `plugin/CMakeLists.txt:508` (`JUCE_USE_CURL`/curl lazy-load) — no libcurl in the NDK sysroot, must exclude Android.
  - `plugin/CMakeLists.txt:533` (`JUCE_JACK=1`) — meaningless on Android, exclude.
  - `plugin/CMakeLists.txt:544` (`JUCE_USE_XINPUT=0`) — X11 concept, exclude for clarity.
  - `plugin/CMakeLists.txt:381-392` — the non-Apple `else()` branch unconditionally does `if (UNIX) find_package(X11 REQUIRED) ... endif()`. **This hard-fails an Android configure** (no X11 in the NDK) and also pulls in `WindowKeyEvents.cpp`, which shouldn't build on Android at all. Needs restructuring into a real three-way branch: APPLE / ANDROID / other-UNIX.
- `test/` exclusion (`CMakeLists.txt:937-939`): extend `if (NOT T3K_IOS)` → `if (NOT T3K_IOS AND NOT T3K_ANDROID)` (the DSP suite is a host-run console binary, can't run cross-compiled).
- Icon block (`plugin/CMakeLists.txt:156-166`): not applicable to Android at the `juce_add_plugin()` level (no `ICON_BIG`-equivalent Android argument exists) — Android's adaptive-icon system belongs entirely in the Gradle project's `res/` tree (Phase 2), sourced from the same full-bleed-square artwork Windows/iOS already use (`icon/icon.png`).

## Phase 2 — Android Studio/Gradle wrapper

New top-level `android/` directory (sibling to `plugin/`, `ui/`, `test/`):
- `android/settings.gradle(.kts)`, `android/build.gradle(.kts)`, `android/gradle.properties`, gradle wrapper files (`gradlew`, `gradlew.bat`, `gradle/wrapper/*`) — checked in per standard Android convention; genuinely new artifact class for this otherwise pure-CMake repo.
- `android/app/build.gradle(.kts)`:
  - `applicationId` matching the existing bundle-id convention (`com.TONE3000.TONE3000`, see `T3K_IOS_BUNDLE_ID` at `plugin/CMakeLists.txt:196`).
  - `externalNativeBuild.cmake { path "../../CMakeLists.txt" }` — pointing at this repo's **existing** root CMakeLists.txt, not a duplicate Android-specific tree. All patch/target/dependency logic stays in `CMakeLists.txt`/`plugin/CMakeLists.txt`; only the outer Gradle project is new.
  - `abiFilters`: `arm64-v8a` at minimum, `x86_64` for emulator convenience.
  - `ndkVersion` pinned explicitly, matching this repo's habit of pinning exact versions (JUCE 9.0.1, ASIO/JACK notes).
- `android/app/src/main/AndroidManifest.xml`: `RECORD_AUDIO`, `INTERNET` permissions (the latter needed by `ProcessorModelLoader::fetchModelFromUrl`), Oboe's low-latency/pro-audio `<uses-feature>` tags, `android:screenOrientation="landscape"` (the Android equivalent of `IPAD_SCREEN_ORIENTATIONS`), `MainActivity extends com.rmsl.juce.JuceActivity`.
- `android/app/src/main/java/.../MainActivity.java`, `JuceApp.java` — modeled on JUCE's own example Android projects; exact minimal override set determined in Phase 0's spike.
- `android/app/src/main/res/mipmap-*/`, adaptive icon XML layers — derived from `icon/icon.png` (same full-bleed-square rule already documented at `plugin/CMakeLists.txt:156-166`); needs either a small new script (parallel to `script/flatten-icon-alpha.swift`) or a one-time manual Android Studio Image Asset export — decide in this phase.
- Java source sets pulling in JUCE's own Android glue classes (`libs/juce/modules/juce_core/native/javacore/app/...`, `juce_gui_basics/native/javaopt/app/...` — verify exact paths against the actually-fetched JUCE 9.0.1 tree in Phase 0, not assumed). Watch the ordering risk: `libs/juce` doesn't exist until the CMake sub-build has run once, so Gradle's Java compilation needs to tolerate that, similar in spirit to (but riskier than) the iOS "configure, build UI, reconfigure" two-pass dance in `docs/ios.md:12-19`.

## Phase 3 — Platform shims

- **`plugin/src/AudioPermissions.cpp`** (currently: `getMicStatus()`/`requestMicAccess()` unconditionally report granted, `openMicSettings()` only branches `JUCE_WINDOWS` — read and confirmed, `plugin/src/AudioPermissions.cpp:1-25`). Unlike Windows/Linux, **Android genuinely enforces `RECORD_AUDIO` at the OS level**, so this file's current "always granted" stub is actually wrong there and needs a real `#if JUCE_ANDROID` branch — check whether `juce::RuntimePermissions` has a working JNI-backed Android implementation in 9.0.1 (would substantially lower this phase's cost vs. hand-rolled JNI).
- **`IosAudioRoute`**: needs **no new code** — its header (`plugin/include/IosAudioRoute.h:26-52`) already has a generic "no-op off iOS" `#else` branch covering every non-iOS platform, Android included.
- **`plugin/src/PresetManager.cpp` — `defaultSystemFactoryDir()`** (`plugin/src/PresetManager.cpp:31-60`, confirmed: falls into a bare `#else return {}` today for any unrecognized platform, i.e. no factory presets would appear on Android unhandled). Needs a new `#elif JUCE_ANDROID` branch. Two real options:
  - **Option A**: JNI `AAssetManager` reads at runtime — more "native," but a real departure from this file's `juce::File`-based approach everywhere else.
  - **Option B (recommended)**: one-time extraction of bundled assets to internal storage on first launch, then treat that directory as an ordinary `juce::File` tree exactly like every other platform — reuses the existing read-only-bundle-plus-user-overlay contract already used for iOS (`docs/ios.md:267-277`), at the cost of a first-run extraction step.
  - Either way, `resources/factory-presets/*.t3kpreset` needs to land in `android/app/src/main/assets/FactoryPresets/` via a Gradle-side copy step, mirroring the iOS `file(GLOB)`-at-configure-time pattern (`plugin/CMakeLists.txt:400-408`).
- **`plugin/src/ProcessorState.cpp`** (`plugin/src/ProcessorState.cpp:28-49`): only carve-out today is `#if JUCE_LINUX || JUCE_BSD` for the bare-`~`-relative default. Android's `userApplicationDataDirectory` should resolve to an already-absolute, app-scoped path (`Context.getFilesDir()`-equivalent) — the existing `#else` fallback likely works unmodified. Verify empirically in Phase 0/1 rather than assume new code is needed.
- **`plugin/src/WindowKeyEvents.cpp`/`.mm`, `WindowMouseEvents.mm`**: should simply not compile on Android (desktop DAW-window keyboard/mouse shims, meaningless for a touch-only standalone). The actual work is making sure Phase 1's restructuring of the `plugin/CMakeLists.txt:381-392` branch excludes them for Android, not writing an Android version.
- **`plugin/src/WebViewCookies.cpp`**: generic (`clearCookies()` only, no Linux-specific symbols) — should compile unchanged on Android via the existing non-Apple branch. Whether it's actually *effective* on Android's WebView is a Phase 4 question, not a Phase 3 code change.
- **`plugin/src/ProcessorModelLoader.cpp`**: no code change expected (uses `juce::URL`/`WebInputStream`) — needs `INTERNET` permission (Phase 2) and live verification (Phase 5), not new code.

## Phase 4 — UI/WebView verification

- **Fixed-window platform flag.** The React UI already has a precedent for exactly this: `IS_IOS`, set via a native-injected `window.__T3K_PLATFORM__ = 'ios'` script at document start (`plugin/src/EditorWebViewSetup.cpp:781-788`, confirmed) and read in `ui/src/hooks/useUiScale.ts:28-29` (confirmed) — its own comment explains why: iOS is "the only build whose window is a fixed, full-screen box... there is no corner drag, no host resize request." A tablet-landscape Android Standalone has the exact same characteristic. Decide explicitly: either add a parallel `'android'` injection and extend every `IS_IOS`/`t3k-ios` consumption site to match it too, or (recommended) generalize the flag from an iOS-specific boolean into something like `IS_FIXED_WINDOW` shared by both platforms, since the underlying reason is now shared, not iOS-specific. This touches shipped iOS behavior, so confirm the naming/semantics before implementing.
- **`IS_COARSE_POINTER`/`html.t3k-touch` reuse needs no new work** — confirmed in `ui/src/hooks/useUiScale.ts:37-48`: it's a pure `matchMedia('(pointer: coarse)')` check, and its own doc comment already explicitly says "iPad, Android and Windows tablets."
- **WebView backend verification — do not assume it "just works."** Every other platform's webview needed hand-patching for exactly this class of problem: the WKWebView white-flash fix, the WebKitGTK SONAME dlopen fix, and most relevantly the WebKitGTK persistent-storage/cookie patch (`CMakeLists.txt:188-301`) — added because stock JUCE on Linux kept OAuth cookies **in memory only**, breaking the tone3000.com session across restarts. Treat Android's Chromium-based system WebView backend as equally unverified:
  - Does the embedded React bundle load/render at all in JUCE's Android WebView component.
  - Does `localStorage` (where OAuth tokens likely live) and the session cookie survive an app restart, or does Android need its own persistent-storage patch analogous to Linux's.
  - Does JUCE's Android WebView backend support `withUserScript`/document-start injection (used for both the platform flag and the background-color/console-forwarding script, `plugin/src/EditorWebViewSetup.cpp:781-796`) — if not, the platform-flag injection point needs a different mechanism.

## Phase 5 — Verification

Environment: Android emulator with a tablet AVD (10"+, forced landscape), physical device pass once the emulator path is solid — mirroring how iOS was driven end-to-end on both Simulator and a physical iPad before slimming down (`docs/ios.md:169-174`).

Build/run loop: likely "Gradle build (triggers the CMake sub-build) → `npm run build` in `ui/` → Gradle build again," analogous to iOS's documented two-pass configure/build-UI/reconfigure dance (`docs/ios.md:12-33`, needed because `plugin/CMakeLists.txt`'s `file(GLOB_RECURSE)` over `webview/*` runs at configure time). Confirm whether Gradle's CMake sub-build re-globs automatically or needs a forced reconfigure.

**Done criteria:**
- App installs and launches without a logcat crash.
- `RECORD_AUDIO` prompt appears; once granted, live input reaches the DSP chain.
- A bundled/factory `.nam` model loads, and a `model_url`-fetched one loads over HTTPS.
- Audio processes end-to-end through Oboe, **input channel correctness specifically verified** (mono in, stereo in, channel-swap checks) given the community-repo author's explicit warning about Android input-channel issues — not just "output produces sound." Note: many emulator/AVD configurations don't pass through a real mic, so this may require a physical device.
- The embedded React UI renders correctly, letterboxed/centered at the right scale.
- OAuth sign-in completes and the session **survives an app restart**.
- Touch ergonomics are visibly active (`html.t3k-touch`, 44pt targets) with no new code required.

## Verification approach

Each phase has its own concrete "done" bar above (Phase 0: trivial app boots on emulator; Phase 5: full done-criteria checklist for the real plugin). Overall: the feature is verified end-to-end by building via Android Studio/Gradle, installing on a landscape tablet emulator and a physical Android tablet, and walking through the Phase 5 checklist manually — this is a GUI/audio app, so it cannot be verified by unit tests alone the way the DSP suite covers desktop.
